# 前端开发规范

新增或修改页面、组件、样式、路由、API 适配、Mock、测试或前端契约前阅读；项目已有更具体规范时，以项目规范为准。

## 1. 开发前检查

- 已读取目标项目 `docs/product/PRD.md` 或确认暂无 PRD。
- 已查看相似页面、共享组件和项目本地规范。
- 已列出页面入口、用户角色、核心动作、成功标准和不做范围。
- 已列出表格列、表单字段、字段来源、状态流转和权限规则。
- 已识别会影响 API/schema/DTO/Mock/测试数据/产品文档的变化。
- 涉及共享 UI 时，已规划至少一个旧页面回归场景。

## 2. 组件和设计系统

优先复用项目已有组件库、表格、弹窗、抽屉、浮层、选择器、按钮、标签、分页、加载遮罩、空态和错误态。新增模式必须说明现有模式为什么不够，并尽量沉淀为可复用组件。

字体、按钮、标签、间距、筛选宽度、弹窗背景、表头、行高、空态、焦点态和语义颜色跟随项目设计系统；不要为单个页面手写一套风格。

页面风格和交互模式优先参考业内大厂同类产品的成熟设计（如 Apple、阿里、字节等已被市场验证的页面风格），避免自造未经验证的交互模式。

## 3. 字段和契约

字段计划建议：

```text
字段 | 来源 | 展示位置 | 是否可编辑 | 提交字段 | 空值 | 校验 | 备注
```

规则：

- 表单 DTO 只包含用户可编辑输入。
- 只读、来源、系统生成、审计、登录上下文和计算字段用文本展示或隐藏。
- 列表、详情、编辑页面使用同一份字段模型。
- API 适配层负责边界类型转换。
- 契约缺失要尽早暴露，不能用 Mock 掩盖。
- 不把 `all`、空字符串、展示文案、路径文案、单位文案或前端专用字段发给 API。

## 4. 表格、表单和弹窗

- 列表保持标题、摘要、筛选、工具栏、数据区、分页的稳定结构。
- 表格先定列宽或最小宽度，再加数据；宽表在表格视口内横向滚动。
- 操作列不换行；时间列、状态列、操作列不能互相挤压。
- sticky 表头必须有不透明背景和正确 z-index。
- 新增、编辑、详情、提交、审核、确认共享同一份字段定义。
- 编辑弹窗必须预填当前数据，详情和终态默认只读。
- 长弹窗限制最大高度，正文滚动，底部按钮可见。
- 重要动作先展示完整详情或确认预览，再二次确认。
- 同一交互区域同一时间只能打开一个 dropdown/popover。

## 5. 交互和异步

查询、重置、刷新、分页和每页条数切换要有短防抖、请求序号或取消机制。写操作必须有提交锁，接口完成前禁用重复操作。

状态不能用普通下拉任意改，要按业务动作按钮触发。保存后列表、详情和表单回显必须一致。成功和失败反馈要对应具体动作。

## 6. 验证要求

完成后至少运行契约检查、构建、相关自动化或 smoke。涉及布局、弹窗、表格、滚动、响应式、交互流程或用户截图反馈时，必须运行 `frontend-browser-qa`。

## 7. 规范缺口和约束强化

发现规范缺口时按问题类型沉淀：

- 显示/代码问题暴露的规范缺口：更新本文件（`frontend-dev-standards/references/frontend-dev-standards.md`）
- 契约规则缺口：更新 `frontend-doc-sync/references/doc-sync-checklist.md`
- 浏览器取证规则缺口：更新 `frontend-browser-qa/references/browser-qa-checklist.md`
- 业务逻辑问题（状态、权限、字段含义、验收标准等）：更新目标项目 `docs/product/PRD.md`
- 重复问题等用户确认后：交给 `frontend-fix-loop`，按其第6节映射表沉淀

无论触发场景是 fix-loop 沉淀、用户直接指出还是 Agent 自发现，都按 `frontend-fix-loop/references/fix-loop.md` 第6节"文档更新指引"执行：全文搜索→判断有无相似规则→强化/改写/新增→输出沉淀文件和动作。
