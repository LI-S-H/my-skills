# 前端代码审核清单

## 1. Diff 范围

先确认：改动符合用户要求；没有无关格式化、误改或大范围重写；新代码符合现有命名、目录、状态管理和样式习惯；当前分支、工作区和 app 目录正确；临时截图、调试脚本、生成产物要么被忽略，要么是有意保留。

分两轮审核：

1. 契约轮：数据、类型、DTO、状态、测试、文档。
2. UI 轮：组件复用、布局、交互、浏览器证据。

构建成功不能替代这两轮审核。

## 2. 组件和布局

- 按钮、弹窗、表格、选择器、标签、分页、加载、空态和错误态优先复用现有组件。
- 表格列宽稳定，没有重叠风险。
- sticky 表头使用不透明背景和正确 z-index。
- 弹窗有最大高度、滚动正文和可见底部按钮。
- 长名称、长编号、长备注有截断或展开方式。
- 修改共享组件时，至少回归一个旧页面。

新实现要和相似页面对比；相似页面用共享组件而新页面手写 CSS 时，除非已说明原因，否则视为风险。

## 3. 数据映射

字段来源交叉检查：

```text
展示字段 | 来源字段/查询 | API 是否返回 | 是否可编辑 | 是否在提交 DTO
```

规则：

- API/schema 响应在清晰边界转换为页面模型。
- 可空字段有明确展示兜底。
- 数字、日期、枚举、ID 不被静默错误转换。
- 新增/编辑 DTO 排除只读、系统生成、审计和展示专用字段。
- Mock fixtures 和文档契约一致。
- 字段没有来源时，要删除、派生或先补契约。

## 4. 事件和状态

每个可见动作都要核对：

```text
按钮/菜单项 | handler | 允许状态 | 禁用状态 | loading/提交态 | 成功结果 | 失败结果
```

检查：按钮有 handler；查询/重置/刷新/分页有即时加载反馈；过期响应会被忽略或取消；写操作有提交锁；重要动作执行前显示详情预览或确认。

## 5. 校验、可访问性和验证

- 必填字段有必填标记、阻断校验和邻近错误提示。
- 弹窗、下拉、二次确认、表格操作的键盘焦点可用。
- 禁用控件在用户需要理解时有原因说明。
- 状态和错误不能只靠颜色表达。

尽量运行最强检查：lint/typecheck、契约/schema 检查、单元或组件测试、生产构建、目标 smoke、变更 UI 的视觉截图或动态交互 Playwright 断言。

如果跳过检查，要说明原因和剩余风险。布局或交互变化必须给出 `frontend-browser-qa` 证据；用户截图反馈要转成回归断言或具名浏览器 QA 场景。

## 6. 输出和分流

发现的问题按三类分类输出，便于后续 skill 处理：

| 问题类别 | 典型发现 | 交给谁 |
| --- | --- | --- |
| 显示问题 | 布局异常、列重叠、截断缺失、样式不一致 | `frontend-browser-qa` 取证后交给 `frontend-fix-loop` |
| 代码问题 | 数据映射错、事件缺、校验缺、提交锁缺、Mock 不一致 | `frontend-fix-loop` |
| 业务逻辑问题 | 状态流转与 PRD 不符、权限规则错、字段含义与业务不符 | `frontend-fix-loop`（沉淀到 PRD） |

每个问题必须标注类别。需要浏览器取证的问题同时说明需要截图的路由、组件和场景，交给 `frontend-browser-qa`。

## 7. 规范缺口沉淀

发现本文件规则缺失或表达不清时，更新本文件（`frontend-code-audit/references/code-audit-checklist.md`）。

无论触发场景是 fix-loop 沉淀、用户直接指出还是 Agent 自发现，都按 `frontend-fix-loop/references/fix-loop.md` 第6节"文档更新指引"执行：全文搜索→判断有无相似规则→强化/改写/新增→输出沉淀文件和动作。
