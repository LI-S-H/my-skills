# 前端代码审核清单

## 1. Diff 范围

- 改动符合用户要求的范围。
- 没有无关格式化、误改或大范围重写。
- 修改共享组件时，至少回归一个旧页面。
- 新代码符合现有命名、目录、状态管理和样式习惯。
- 当前分支、工作区和 app 目录都和任务一致。
- 临时截图、调试脚本、生成产物要么被忽略，要么是有意暂存。

分两轮审核：

1. 契约轮：数据、类型、DTO、状态、测试、文档。
2. UI 轮：组件复用、布局、交互、浏览器证据。

构建成功不能替代这两轮审核。

## 2. 组件和布局

- 按钮、弹窗、表格、选择器、标签、分页、加载、空状态、错误状态优先复用现有组件。
- 表格列宽稳定，没有重叠风险。
- sticky 表头使用不透明背景和正确 z-index。
- 弹窗有最大高度、滚动正文和可见底部按钮。
- 长名称、长编号、长备注有截断或展开方式。

把新实现和编码前找到的相似页面对比。如果相似页面用共享组件，而新页面手写 CSS，要视为风险，除非差异是有意且已说明。

## 3. 数据映射

- API/schema 响应在清晰边界转换为页面模型。
- 可空字段有明确展示兜底。
- 数字、日期、枚举、ID 不被静默错误转换。
- 新增/编辑 DTO 排除只读、系统生成、审计和展示专用字段。
- Mock fixtures 和文档契约一致。

字段来源交叉检查：

```text
展示字段 | 来源字段/查询 | API 是否返回 | 是否可编辑 | 是否在提交 DTO
```

如果字段没有来源或 API 无法返回，要删除、由前端用已有数据派生，或先补契约再交付。

## 4. 事件和状态

- 每个可见按钮都有预期 handler。
- 查询、重置、刷新、分页、每页条数切换都有即时加载反馈。
- 过期响应会被忽略或取消。
- 写操作有提交锁，不能重复触发。
- 重要动作执行前显示详情预览或确认。

每个可见动作都要核对：

```text
按钮/菜单项 | handler | 允许状态 | 禁用状态 | loading/提交态 | 成功结果 | 失败结果
```

## 5. 校验和可访问性

- 必填字段有必填标记、阻断校验和邻近错误提示。
- 弹窗、下拉、二次确认、表格操作的键盘焦点可用。
- 禁用控件在用户需要理解时有原因说明。
- 状态和错误不能只靠颜色表达。

## 6. 验证

尽量运行最强的一组检查：

- lint 或 typecheck
- 契约/schema 检查
- 单元测试或组件测试
- 生产构建
- 目标 smoke 测试
- 变更 UI 的浏览器截图

如果跳过检查，要说明原因和剩余风险。

证据规则：报告路由和流程，不只报告命令。“构建通过”不足以证明 UI 工作完成；布局或交互有变化时，必须给出浏览器 QA 目录或截图证据。

如果用户反馈来自浏览器评论或截图，要把每条评论转成回归断言或具名浏览器 QA 场景。视觉评论只有在同一元素、同一视口被新截图或断言覆盖后，才算关闭。

## 7. 长期维护位置

审核漏项要沉淀到明确文件：

- 通用代码审核清单：更新 `frontend-code-audit/references/code-audit-checklist.md`。
- 可脚本化的检查命令或参数：更新 `frontend-code-audit/scripts/run-frontend-gate.cjs`。
- 通用开发规范缺口：更新 `frontend-dev-standards/references/frontend-dev-must-read.md`。
- 浏览器 QA 场景缺口：更新 `frontend-browser-qa/references/frontend-product-qa-checklist.md` 和 `frontend-browser-qa/references/browser-qa-checklist.md`。
- 用户认可后的重复问题：更新 `frontend-fix-loop/references/frontend-issue-record.md`。

如果问题是“已有清单写了但没执行”，不要新增重复条目，改为在原条目前加明确强制措辞。
