# 契约同步清单

UI 和数据契约互相影响时使用本清单。

## 1. 字段清单

超过 5 个字段变化时，用矩阵，不写散文：

```text
UI 标签 | API/schema 字段 | 类型 | 来源 | 可编辑 | 必填 | 空值展示 | 测试数据
```

每个字段必须明确 UI 名称、契约字段名、类型、是否可空、来源、可编辑性、校验规则和空值展示。

## 2. API 和 Schema

按项目实际情况同步：OpenAPI、GraphQL schema、tRPC router、REST 文档、protobuf、JSON schema、请求/响应 DTO、API 适配器、Mock 服务、fixtures、seed data、示例 payload 和错误响应。

不要把项目专属字段、业务表名或接口路径写进通用 skill；这里只记录可迁移的同步方法。

## 3. 状态和动作契约

工作流页面必须记录：页面状态、每个状态允许动作、权限要求、可编辑字段、预览/二次确认、终态和反向/撤销规则。

状态动作表：

```text
状态 | 可见动作 | 可编辑字段 | 动作前必填字段 | 确认方式 | 结果状态
```

这能避免列表显示了动作，但编辑/详情弹窗不支持；也能避免状态被做成自由下拉。

## 4. 测试和数据

同步测试：正确新增/编辑 payload、必填为空 payload、长文本和空值列表响应、详情响应、权限不足响应、动作禁用响应、冲突或校验失败响应。

测试数据至少包含长文本、空值、停用/不可选关联选项、多种状态、足够触发分页和滚动的行数。

## 5. 停止条件

遇到这些情况先停下来澄清或补契约：

- UI 需要的字段没有任何契约能提供。
- 契约暴露了不应该编辑的字段。
- Mock 数据和文档 API 不一致。
- 前端只能靠猜后端行为才能工作。
- 页面想展示昂贵全量聚合摘要，但用户其实只需要当前页决策；除非 PRD 明确需要总数，否则优先当前页业务指标或无总数分页。

## 6. 规范缺口沉淀

发现本文件规则缺失或表达不清时，更新本文件（`frontend-doc-sync/references/doc-sync-checklist.md`）。

无论触发场景是 fix-loop 沉淀、用户直接指出还是 Agent 自发现，都按 `frontend-fix-loop/references/fix-loop.md` 第6节"文档更新指引"执行：全文搜索→判断有无相似规则→强化/改写/新增→输出沉淀文件和动作。
