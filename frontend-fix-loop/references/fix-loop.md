# 前端修复闭环

## 1. 分类和复现

先判断问题类型，分三类：

| 类别 | 典型表现 | 沉淀目标 |
| --- | --- | --- |
| **显示问题** | 视觉错乱、布局破、表格重叠、sticky 透明、截断不合理、响应式异常 | skill 长期维护文件 |
| **代码问题** | 数据映射错、事件绑定缺、校验缺、提交锁缺、Mock 不一致、测试缺失 | skill 长期维护文件 |
| **业务逻辑问题** | 状态流转不符合业务、权限规则错、字段含义/来源/口径与业务不符、流程缺口、验收标准缺失 | 目标项目 `docs/product/PRD.md` |

每类问题修复后必须执行沉淀检查：读取第6节映射表中对应的长期维护文件，对比本次问题，判断是否有规则缺失或表达不清需要补充。

复现证据优先级：用户截图、本地浏览器截图、DOM 检查、测试数据、smoke 测试、控制台或网络日志。视觉问题只要能低成本看到，就不要凭记忆修改。

如果反馈是"还在要求旧依赖"或"页面还是旧版本"，先查分支、当前提交、package 文件、源码引用和依赖安装状态。

## 2. 历史问题查重

修复前查 `frontend-fix-loop/references/frontend-issue-record.md` 是否已有类似项，例如表格列重叠、sticky 透明、弹窗滚动、编辑无预填、按钮标签不一致、缺 loading 或提交锁。

已有方案仍适用时优先复用。没有记录时按症状、层级、相似组件和验证要求临时归纳；永久记录必须等用户认可修复成功后再写。

## 3. 修复顺序

1. 复现原问题。
2. 按第1节三类判断根因属于显示、代码还是业务逻辑，再细分到组件、样式、数据映射、事件、契约、状态、权限或环境。
3. 在能解释问题的最低共享层修复。
4. 保留用户已有改动和无关工作。
5. 契约错误同步给 `frontend-doc-sync`。
6. 运行最小聚焦检查。
7. 显示问题必须运行 `frontend-browser-qa` 重新取证。
8. 代码问题必须重新运行 `frontend-code-audit` 审核修复后的 diff。
9. 业务逻辑问题运行或交给 `frontend-product-acceptance`。

能自动回归的问题要加测试或更新测试。

## 4. 验证

最低验证：相关静态检查、构建或测试命令；受影响 smoke 或交互脚本；用户原始反馈场景。

视觉问题必须重新截图。浏览器 QA 类修复必须覆盖相同视口和相同目标区域；原截图标注了下拉、单元格或弹窗字段，新证据也必须覆盖同一表面。

## 5. 用户认可后的记录和文档沉淀

用户说"可以了、通过、没问题、已解决、这次对了"等认可语句后：

1. 回看最近一次修复或 QA 的问题事实。
2. 判断是否属于可复用长期问题；一次性业务问题不写通用记录。
3. 查重 `frontend-fix-loop/references/frontend-issue-record.md`。
4. 如果发现长期规则缺失或表达不清，按第6节"文档更新指引"执行定位、搜索、强化/新增和输出。

记录格式：

```text
问题类别：显示问题 / 代码问题 / 业务逻辑问题（必填）
症状：（必填）
根因：（必填）
认可的修复：（必填）
后续规则：（必填）
长期沉淀文件：显示/代码问题填 skill 文件路径，业务逻辑问题填目标项目 PRD 路径（必填）
沉淀动作：新增规则 / 强化已有规则（必填）
验证：（必填）
```

不要在用户认可前写永久问题记录；但如果本次修复已经暴露出文档规则缺失或表达不清，修复汇报时要先指出应该修改哪个长期维护文件。

## 6. 长期维护文件位置和更新指引

发现需要沉淀时，按问题类型和性质选择文件，并按本节操作步骤执行更新。

### 显示问题和代码问题 → skill 长期维护文件

### 触发场景

无论通过哪种场景触发，更新长期维护文件时都遵循相同的操作步骤。

| 场景 | 说明 | 示例 |
| --- | --- | --- |
| fix-loop 沉淀 | 修复问题后，用户确认，暴露出规则缺失 | 修了表格列重叠后，发现 dev-standards 没有列宽规划规则 |
| 用户直接指出 | 用户明确说某个清单漏了规则或规则有误 | 用户说"需求清单没有提到批量操作" |
| Agent 自发现 | 使用 skill 时发现规则缺口 | code-audit 时发现没有检查 disabled 原因说明 |

### 操作步骤

1. **定位文件**：按上面两个映射表（skill 文件或 PRD）找到目标文件。
2. **全文搜索**：在目标文件中搜索与本次问题相关的关键词，判断是否已有相似规则。如果不确定，先全文搜索关键词再决定。
3. **决定动作**：
   - **有相似规则但没有被执行** → 强化原条目：补充"必须"、增加具体操作步骤、加入反面案例。禁止另写新条目。
   - **有相似规则但表达不清** → 改写原条目：把本次问题合并进去，让规则更具体、更容易执行。禁止另写新条目。
   - **没有相似规则** → 在对应章节末尾新增一条简短规则。不要因为同一问题在多个文件里重复写一遍，除非它确实影响多个阶段。
4. **写法要求**：规则要短、可执行，写"做什么"而非"注意什么"；用"必须/禁止"表达强制要求，不用"建议/尽量"；如果规则容易被违反，补充违反时的后果或检查方式。
5. **输出**：必须写明 `长期沉淀文件：<路径>`、`沉淀动作：强化已有规则 / 新增规则`、修改的具体位置。
