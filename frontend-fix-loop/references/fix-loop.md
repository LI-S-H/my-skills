# 前端修复闭环

## 1. 问题分类

先判断问题类型：

- 视觉：重叠、间距、颜色、字号、sticky 表头、滚动、响应式
- 数据：字段错误、字段缺失、映射错误、Mock 过期、DTO 错误
- 交互：按钮未绑定、下拉错误、加载缺失、重复提交
- 流程：状态错误、缺确认、权限错误、不可逆动作太容易执行
- 契约：后端/API/schema 无法提供页面展示内容
- 环境：分支不对、app 目录不对、依赖安装过期、已移除的库仍被要求

## 2. 复现

使用最强可用证据：

- 用户截图
- 本地浏览器截图
- DOM 检查
- 测试数据
- smoke 测试
- 控制台或网络日志

视觉问题只要能低成本看到，就不要凭记忆修改。

如果反馈是“还在要求旧依赖”或“页面还是旧版本”，先检查分支、当前提交、package 文件、源码引用和依赖安装状态，再改应用代码。

## 3. 对照历史问题

修复前先查问题记录中是否有类似项：

- 表格列重叠
- sticky 表头透明
- 弹窗滚动问题
- 编辑弹窗无数据
- 按钮或标签不一致
- 缺 loading 或提交锁
- 摘要指标口径错误
- 长文本撑破布局

如果已有方案仍适用，优先复用。

如果没有本地问题记录，临时按“症状、可能层级、相似组件、验证要求”归纳。永久记录必须等用户认可后再写。

## 4. 修复

- 重复显示类问题优先在组件层修。
- 改动范围保持最小。
- 保留用户已有改动和无关工作。
- 问题证明契约错误时，同步更新文档/契约。
- 能自动回归的问题要加测试或更新测试。

修复顺序：

1. 复现原问题。
2. 判断根因属于需求、契约、组件、样式、状态还是测试。
3. 在能解释问题的最低共享层修复。
4. 运行最小聚焦检查。
5. 视觉/交互问题运行浏览器 QA。
6. 用户认可后再更新文档或问题记录。

## 5. 验证

最低验证：

- 运行相关静态、构建或测试命令。
- 运行受影响 smoke 或交互脚本。
- 视觉问题必须重新截图。
- 复测用户原始反馈场景。

浏览器评论类修复，要验证相同视口和相同目标区域。如果原截图标注了下拉、单元格或弹窗字段，新证据也必须覆盖同一表面。

## 6. 记录

只有用户认可修复后，才写入永久问题记录：

- 增加一条简短记录。
- 包含症状、认可的修复方案和后续规则。
- 避免长篇叙述。
- 如果问题已在规范里写过但本次没遵守，强化措辞，不重复加行。

记录格式：

```text
症状：
根因：
认可的修复：
后续规则：
验证：
```

## 7. 用户确认后的补记流程

用户后续只说“可以了、通过、没问题、已解决、这次对了”时，也要执行这一段：

1. 回看最近一次前端修复或浏览器 QA 的问题事实。
2. 判断是否属于可复用的长期问题；只影响当前业务的一次性问题不写入通用记录。
3. 先查 `frontend-fix-loop/references/frontend-issue-record.md` 是否已有同类条目。
4. 已有条目：只在必要时强化对应规范，不重复加行。
5. 没有条目：追加一条短记录，包含问题、认可方案、后续规范。
6. 如果问题暴露的是开发规范或浏览器 QA 漏项，同步更新对应 skill 的 `references/`。

不要在用户还没认可时提前写记录；也不要因为用户认可语句很短就跳过记录判断。

## 8. 长期维护位置

修复记录和规范沉淀必须写到明确文件：

- 重复问题记录文本：写入 `frontend-fix-loop/references/frontend-issue-record.md`。
- 通用前端开发规范缺口：写入 `frontend-dev-standards/references/frontend-dev-must-read.md`。
- 浏览器验收清单缺口：写入 `frontend-browser-qa/references/frontend-product-qa-checklist.md`。
- 修复闭环流程本身：更新 `frontend-fix-loop/references/fix-loop.md`。
- 某个专项 skill 的规则缺口：更新对应 `<skill-name>/references/*.md`。
- 可复用脚本缺口：更新对应 `<skill-name>/scripts/*`。
- 技能包结构、触发时机或调用顺序变化：更新 `frontend-skill-index/references/frontend-skill-package.md` 和 `frontend-skill-index/SKILL.md`。

重复问题只有在用户确认“这次修好了、方案认可”后，才能写入 `frontend-fix-loop/references/frontend-issue-record.md`。如果同类问题再次发生，先查该文件；若已有规则但没遵守，需要在回复中说明漏遵守，并强化相应规范条目。
