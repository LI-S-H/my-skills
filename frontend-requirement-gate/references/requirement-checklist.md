# 需求澄清清单

## 1. 产品意图

- 用户要通过这个 UI 完成什么任务？
- 涉及哪个路由、页面、弹窗、抽屉、表格或组件？
- 这是新流程、旧流程修改，还是视觉修复？
- 本次明确不做什么？

## 2. 用户动作

列出用户可以执行的所有动作：

- 新增、编辑、查看详情、删除、停用、启用
- 提交、审核、驳回、确认、取消
- 查询、重置、刷新、分页、导出、导入
- 展开/收起明细、选择行、批量操作

重要或不可逆动作必须先展示详情预览或确认界面，再执行。

## 3. 数据来源

对每个展示字段分类：

- 用户输入
- 服务端生成
- 当前登录用户上下文
- 审计字段
- API/schema 字段
- 关联查询或聚合字段
- 前端字典或派生展示值

可编辑字段和提交 DTO 字段必须只来自“用户输入”。来源字段、审计字段、系统生成字段和只读字段不能误做成可编辑控件。

## 4. 状态规则

定义每个状态下允许的动作。常见例子：

- 草稿：可编辑、可提交、可删除
- 已提交/待处理：通常只允许有权限的人审核、驳回或有限编辑
- 已确认/已审核/终态：默认只读，除非业务明确支持反向单据或撤销
- 停用/删除：不能被新记录选择，但历史引用仍可展示

如果状态变化会写入业务事实，不要把它建模成自由下拉框。

## 5. 验收标准

验收标准至少包含：

- 新增后能在列表查到
- 编辑弹窗能带出当前值
- 详情数据和列表、保存结果一致
- 必填字段为空时阻止提交，并在字段附近提示
- 重要动作先预览或确认再执行
- 加载、错误、空状态、成功状态都可见
- 目标视口下布局不破

## 6. 编码前证据

编码前先收集足够证据，避免靠猜：

- 可复用的相似页面或组件
- 每个展示字段和可编辑字段的来源
- 预期 API/schema 请求和响应结构
- 状态和动作矩阵
- 本次验收需要的截图或浏览器流程

如果有未知项，明确写出假设。只有当缺失信息会影响数据正确性、权限、不可逆动作或可见流程时，才必须先问用户。

## 7. 需求复述模板

编码前使用这个简短模板：

```text
目标：
页面/组件：
用户动作：
可编辑字段：
只读/系统生成字段：
状态和允许动作：
需要同步的契约/文档：
浏览器 QA 场景：
假设：
```

## 8. 长期维护位置

发现需求澄清流程有长期复用价值时，按下面位置沉淀：

- 通用开发前必读规则：更新 `frontend-dev-standards/references/frontend-dev-must-read.md`。
- 需求澄清清单本身：更新 `frontend-requirement-gate/references/requirement-checklist.md`。
- 技能调用顺序或职责变化：更新 `frontend-skill-index/references/frontend-skill-package.md` 和 `frontend-skill-index/SKILL.md`。
- 已被用户认可的重复问题：更新 `frontend-fix-loop/references/frontend-issue-record.md`，不要写在本清单里。

只有用户认可“这个规则以后也要遵守”后，才写入长期文档；临时假设只放在本次回复或任务记录中。
