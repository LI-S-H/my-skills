# 需求澄清清单

## 1. 开工前必须明确

- 目标：用户要通过这个 UI 完成什么业务任务。
- 范围：涉及页面、路由、弹窗、表格、组件，以及明确不做的内容。
- 角色：谁使用，谁审核，谁只能查看。
- 动作：新增、编辑、详情、删除、提交、审核、驳回、确认、导出、分页、筛选等。
- 字段：展示字段、可编辑字段、只读字段、系统生成字段、审计字段。
- 状态：每个状态允许哪些动作，终态是否只读。
- 验收：什么结果算通过，哪些浏览器 QA 场景必须覆盖。

## 2. 字段和数据来源

每个字段都要标明来源：用户输入、服务端生成、登录上下文、审计字段、API/schema、关联查询、聚合结果、前端字典或前端派生值。

规则：

- 提交 DTO 只包含用户可编辑输入。
- 来源字段、审计字段、系统生成字段和只读字段不能误做成可编辑控件。
- 字段来源不清时先标为假设；影响数据正确性时必须确认。

## 3. 状态和高风险动作

- 草稿通常可编辑、可提交、可删除。
- 待处理通常只允许有权限的人审核、驳回或有限编辑。
- 已确认、已审核、已完成等终态默认只读。
- 停用或删除的数据不能被新记录选择，但历史引用仍要可展示。
- 提交、审核、删除、作废、停用等高风险动作必须有预览或二次确认。

如果状态变化会写入业务事实，不要把它建模成自由下拉框。

## 4. 最低验收标准

- 新增后能在列表查到。
- 编辑弹窗能带出当前值。
- 详情、列表和保存结果一致。
- 必填为空时阻止提交，并在字段附近提示。
- 重要动作先预览或确认再执行。
- 加载、错误、空态、成功态都可见。
- 目标视口下布局不破。

## 5. 需求复述模板

```text
目标：
页面/组件：
用户角色：
用户动作：
可编辑字段：
只读/系统生成字段：
状态和允许动作：
需要同步的契约/文档：
浏览器 QA 场景：
假设/待确认：
```

只有缺失信息影响数据正确性、权限、不可逆动作或核心流程时，才必须先问用户；其他情况先基于假设推进，并把假设交给 `frontend-product-docs` 写入 PRD 待确认项。

## 6. 规范缺口沉淀

发现本文件规则缺失或表达不清时，更新本文件（`frontend-requirement-gate/references/requirement-checklist.md`）。

无论触发场景是 fix-loop 沉淀、用户直接指出还是 Agent 自发现，都按 `frontend-fix-loop/references/fix-loop.md` 第6节"文档更新指引"执行：全文搜索→判断有无相似规则→强化/改写/新增→输出沉淀文件和动作。
